# Fork engineering instructions

This checkout is the LastMile Innovations fork of God's Eye View. The unified NeighborOS / Quanta World direction is documented in [the integration guide](docs/UNIFIED-WORLD.md). Start from the [single master specification](../NEIGHBOROS_MASTER_SPEC.md). A bounded native workspace is built locally; the broader unified product remains staged and REVIEW_PENDING. See [runtime instructions](docs/NEIGHBOROS.md).

## Start with the right evidence

- Read [documentation map](docs/README.md), [current runtime state](docs/CURRENT-STATE.md), [component boundaries](docs/CODE-BOUNDARIES.md), and affected source/tests.
- Inspect Git status and preserve others' changes. Do not reset, broadly stage, clean or rewrite supplied work.
- Distinguish existing behavior, local checks and proposed interfaces. Candidate Quanta/NeighborOS contracts do not establish running services.
- Use declared package exports, injected sources and application operations. Preserve lifecycle cleanup, cancellation, attribution, stable share-token meanings and camera ownership.

## Integration rules

- NeighborOS and Quanta World are one product. Quanta owns canonical records; browser state, indexes and scene projections are disposable.
- Keep independent source occurrences, original evidence, conflicting claims, units and time semantics. Unavailable is not empty; simulated/predicted/authored information is not observation.
- The existing standalone application is once per page. Do not claim repeatable panel mounting or multiple viewer support without refactoring and testing that ownership.
- Local provider/MCP guards and panel keys are not user authentication. Do not expose local routes as a hosted multi-user API.
- Models propose; current domain authority governs writes. Never infer access from a QID, URL, old snapshot or requested persona.
- Keep private data and provider secrets out of public links, logs, browser bundles and scene exports. Retain browser-supported public-key restrictions separately from server-secret handling.
- Preserve code/data/model notices. Review display, retention, derivation and export separately. A disabled layer does not remove restricted bundled bytes from distribution.

## Verification and reporting

Use the pinned supported Node runtime and lockfile. See [contributor guide](CONTRIBUTING.md) for build/unit/tracking and affected feature gates. For documentation-only changes, check links, source references, instruction consistency and disposition inventory; no runtime changelog fragment or performance claim is needed. Run relevant runtime gates when behavior changes.

Freeze behavior/outcome tests and a reproducible baseline before optimization; retain failures and raw measurements. Do not change expected results simply to obtain a pass. Separate provider/network failures from implementation failures. Two model opinions are not an independent oracle.

Do not spawn agents unless explicitly authorized. Do not push, deploy, merge, spend, enable providers or message others without task authorization. Completion reports name changed paths, actual checks, failures/skips and unresolved gates. Use DESIGNED, BUILT_LOCAL, TESTED_LOCAL, REVIEW_PENDING and ENABLED_LIVE accurately.
